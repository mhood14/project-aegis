AI security & agentic controls

Designing AI systems that stay inside security boundaries.

Project Aegis frames AI security around authorization, retrieval integrity, human approval, and auditability. The goal is not just to build an AI assistant, but to show how an AI-enabled system can be governed and investigated.

Agentic security model

Recommendations are allowed. Privileged execution is controlled.

As AI systems move from answering questions toward recommending or triggering actions, the security boundary changes. Project Aegis documents that distinction explicitly.

✅

Allowed

  • Answer questions using authorized retrieved context.
  • Cite supporting document chunks.
  • Recommend investigation next steps.
  • Log user, scope, request ID, and retrieved references.
⛔

Not allowed

  • Bypass server-side authorization.
  • Retrieve content outside the user’s scope.
  • Modify access policies or security settings.
  • Execute privileged actions based only on model output.
👤

Requires human approval

  • Access changes and privilege elevation.
  • Incident closure or remediation actions.
  • Document classification changes.
  • Bulk data export or sensitive workflow execution.

Risks and controls

AI-specific risks mapped to concrete security controls.

The project treats retrieved content and model output as untrusted. Authorization and security decisions remain deterministic application controls, not instructions delegated to the model.

Prompt injection

Malicious instructions in user input or retrieved documents

Control: Retrieve only authorized context, frame documents as untrusted, strip obvious injection patterns as defense-in-depth, log sanitization events, and investigate content-filter triggers in Sentinel.

Excessive agency

AI performs sensitive actions without appropriate approval

Control: Keep the current design recommendation-only, define human approval gates, and require separate authorization checks before any future tool or workflow execution.

Retrieval abuse

User or compromised account probes document scopes

Control: Enforce scope checks server-side, emit authorization-denied events, and alert on repeated denials or unusual scope usage through Sentinel/KQL detections.

Weak auditability

Security teams cannot reconstruct what the AI saw or did

Control: Log request IDs, user identity, selected scope, document IDs, sanitization outcomes, model safety blocks, and completion status for investigation in Log Analytics.

AI security test plan

Security tests focus on behavior, evidence, and detection opportunities.

These scenarios are designed to make secure AI behavior observable rather than relying on a claim that the model “should” behave safely.

01

Unauthorized retrieval attempt

Expected behavior: Request is denied before retrieval, no unauthorized context is sent to Azure OpenAI, and an authorization_denied event is logged.

Detection opportunity: Alert on repeated denials, new source patterns, or scope probing from the same identity.

02

Indirect prompt injection in a retrieved document

Expected behavior: Retrieved text is treated as data, suspicious instructions are sanitized when detected, and citations remain grounded in authorized content.

Detection opportunity: Track retrieved_content_sanitized and content-filter events for suspicious documents or repeated attempts.

03

Request to reveal hidden instructions or sensitive data

Expected behavior: The model response stays within retrieved authorized context, avoids hidden/system prompt disclosure, and logs blocked or unsafe behavior where applicable.

Detection opportunity: Review content-filter triggers and repeated sensitive-data extraction patterns.

04

Future agent action request

Expected behavior: The AI may recommend an action, but privileged execution requires deterministic authorization and human approval outside model output.

Detection opportunity: Log recommendation metadata, requested action type, approver identity, approval outcome, and request ID for investigation.
