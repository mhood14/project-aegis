Recruiter-ready case study

Secure AI on Microsoft Azure.

Project Aegis is a security engineering portfolio project focused on one problem: how to let users ask questions over internal documents with AI without turning retrieval, identity, and agent behavior into a data exposure risk.

🎯

Problem

Organizations want AI over internal knowledge, but insecure RAG systems can retrieve unauthorized content, follow malicious document instructions, leak sensitive data, or leave security teams without useful investigation evidence.

🛡️

Security objective

Design the system so identity, authorization, scoped retrieval, logging, and monitoring are part of the architecture from the start rather than being bolted on after the AI feature works.

Solution summary

A secure RAG reference architecture built around Microsoft security primitives.

The application combines Microsoft Entra-backed access, Azure OpenAI, Azure AI Search, Blob Storage, managed identity-oriented service access, structured audit events, Microsoft Sentinel detections, KQL hunting queries, and threat modeling for AI-specific risks.

1

Authenticate

Users enter through Microsoft identity / App Service auth, giving the app an identity context before retrieval or upload decisions are made.

2

Authorize

Server-side scope checks determine which document collections a user can access. UI selections do not grant permission.

3

Retrieve safely

Azure AI Search returns scoped context, retrieved content is treated as untrusted data, and Azure OpenAI produces grounded answers with citations.

4

Monitor

Structured JSON events support Log Analytics and Sentinel investigations for prompt injection, authorization abuse, suspicious scope use, and unsafe content handling.

What this demonstrates

Designed for Microsoft cloud security and AI-security conversations.

This project is intentionally positioned as a portfolio artifact for Microsoft security, secure AI, cloud security architecture, and agentic security roles.

🔐

Identity-aware AI

Retrieval is constrained by user scope, authorization is enforced server-side, and future production hardening points toward Entra group-to-scope mapping and least-privilege RBAC.

🤖

Agentic security thinking

The design separates recommendations from execution, calls out human approval boundaries, and treats tool use, retrieval, and autonomous actions as security-sensitive events.

📊

Security operations visibility

Sentinel detections and KQL examples turn AI and app behavior into triageable signals instead of leaving security teams with only application screenshots.

Role relevance

Why this project matters for Microsoft security and AI work.

Project Aegis was built to show how secure AI systems require more than a working model call. The important engineering decisions are identity, authorization, retrieval scope, monitoring, and human control over sensitive actions.

🧭

Security engineering value

  • Uses Microsoft Entra-backed access and server-side scope checks so retrieval follows user authorization instead of UI preference.
  • Connects Azure OpenAI, Azure AI Search, Blob Storage, and managed identity-oriented access into a secure RAG architecture.
  • Turns application behavior into structured audit events that can support Sentinel detections, KQL hunting, and investigation workflows.
  • Documents production hardening needs such as stronger RBAC mapping, private endpoints, detection-as-code, and AI safety testing.
🤖

AI security value

The project treats retrieved content and model output as untrusted inputs. Prompt injection, indirect prompt injection, retrieval abuse, excessive agency, and weak auditability are handled as security architecture concerns, not just model-quality concerns.

Future agentic workflows are intentionally bounded: the AI can recommend next steps, but privileged execution requires deterministic authorization, explicit approval, and traceable audit logs.
